# Token2API 产品路线：AI Native × Web3 Native

> 产品研究与设计草案，更新于 2026-10-17。本文区分**现有能力**与**拟建设能力**，不把规划当作已上线功能。当前可复现的闭环见[五分钟本地演示](./PRODUCT_DEMO.md)，工程验收状态见[开发任务](./TASKS.md)。

## 产品判断

Token2API 应定位为**面向 AI 开发者的双边资源市场和预付费结算层**：提供者把自己有权售卖的模型网关上架并报价；买方在模型广场选择资源、确定预算和支付方式，再把会话 Key 装进现有工具；请求按用量记账，提供者获得收入，消费者取回未用预算。

买方得到的是可选供给、明确单价和费用上限，且可核对一次调用到一笔账单的关系。卖方得到的是接入、报价和收款能力。链上路径的额外价值是合约约束预算、公开可查的结算事件、向原消费者归属的退款和可按地址核对的提供者收入。链下路径可覆盖不使用钱包的人，但其退款和到账规则取决于支付机构及平台账本，不能称为同等的链上保证。

**AI Native** 表示买方从正在使用的 AI 工具进入市场，看到真实可用的模型能力、协议、价格和余额；卖方从已有网关或工具配置导入资源，经过授权与调用验证后上架。**Web3 Native** 表示钱包、预算托管和提款是完整可用的一种支付路径，提供者分账与消费者退款都有链上证据，而不是在 AI 页面贴一个钱包按钮。

市场上已有模型聚合、定价展示、路由、额度控制、开放供给和加密货币付款。通用 API 市场的商业规则也可参考 [RapidAPI 对开发者的付款说明](https://docs.rapidapi.com/docs/payouts-and-finance)及 [Apify 按事件付费的卖方收益规则](https://docs.apify.com/actors/publishing/monetize/pay-per-event)，但它们的商品和分成口径不同，不能拿各家的百分比直接比较。Token2API 若只复制入口与支付方式，缺少可信优势。先证明**卖方可以实际接入并获得收入，买方能够在熟悉的 AI 工具里调用、看懂费用、退出并取回未用资金**；再谈更广的流量与经济模型。平台当前 5% 是**已结算用量的分成**，与 OpenRouter 的**买方 credits 购买费**、Requesty 的**充值费**不在同一计费基数，不能只按百分比排高低。这条分成规则也不是已验证的盈利能力：后续须量化获取卖方、审核、支付手续费、链上交易、坏账和客服成本。

**首批目标用户**可以是已有合法网关、希望新增分发和结算渠道的小型提供者，以及已经在 Magpie/CC Switch 管理 API 的开发者。先以少量真实资源验证成交：从「看见报价」到「实际调用」的转化、每个提供者完成的有效账单、使用者复购、退款完成时间、人工核对占比和提供者实际到账。市场规模和收入没有可用的本项目实测样本，不能从竞品公开价推算；没有数据前，不声称便宜、低延迟、高可用或有规模化需求。

**价格不是唯一价值**。买方还在意是否真正支持工具调用、推理模式、上下文长度、缓存、响应速度和任务稳定性；卖方还在意封号/转售权限、费后净收入、结算周期和可撤回权限。模型广场在有真实测量前只显示「未验证」，不把卖方自报的能力或演示请求混进服务质量指标。

**单位经济验收**：先按一次完整预算会话核算，而非只看调用次数。买方实际成本包括挂牌用量费、支付或兑换手续费及未退还的资金成本；卖方净额按合约结算规则为已结算用量减去 5% 平台费，再扣自己的上游和运营成本。平台的毛收入是已结算用量的 5%；还要逐会话扣除支付手续费、链上交易、补贴、人工核对、失败结算损失和客服成本。结算采用累计批次，不能把一次模型请求当成一次链上交易来估算成本。先记录真实样本和完成时间，再决定平台费率与最低预算。

首批试点记录这些可核查数据；样本不足时只报告原始数量，不用百分比推断市场规模：

| 指标 | 记录方式 | 回答的问题 |
| --- | --- | --- |
| 卖方有效上架 | 有使用与转售授权、真实响应、最终 usage 和请求 ID 的资源数 / 尝试接入的资源数 | 有多少供给真正可卖？ |
| 买方首次完成调用 | 首次看见该真实资源后，完成资金确认、目标工具调用与对应账单的人数 / 实际查看该资源的人数 | 买方能否从选择走到使用？ |
| 账单核对与异常 | 完成请求中可对应上游 ID、最终 usage 与费用的数量；另列 REVIEW 数量、原因和人工处理时间 | 计费证据是否足够，异常要花多少人力？ |
| 资金时间与净额 | 分别记录开通确认、账单确认到提供者可提现、关闭到消费者可提现、双方提取到账时间；逐笔核对交易费与最终净额 | 链上路径相对链下方式的收益与成本是否成立？ |

## 模型广场：官方参考价与平台挂牌价

入口从“按资源找资源”升级为“先按可验证模型找能力，再选提供者”。模型卡包含协议能力（文本、流式、工具、多模态分别标注已验收/未支持）、提供者与状态、最低购买预算、付款方式和报价。点击模型后按提供者列出挂牌价，再进入购买确认。提供者自填的模型名称只能作为**声明**，不能自动当成官方模型身份。

| 价格字段 | 来源与显示方式 |
| --- | --- |
| **官方参考价** | 对应模型厂商官网可核查的公开按量价；保存厂商、官方模型 ID、价格页面 URL、采集时间、币种、计费层级、输入/输出每百万 Token 单价。没有可比价就写“暂无可比官方价”。 |
| **平台挂牌价** | 卖方为其资源设定的买方价格，分别显示输入/输出每百万 Token，明确币种及手续费是否已包含。卖方声明的型号与计费层级须单独验证，挂牌本身不构成官方型号证明。当前合约中买方按挂牌价扣费，5% 从结算金额中分给平台，提供者净得剩余部分。 |
| **对比** | 仅在模型身份、上下文区间、缓存/批处理、地区、输入/输出口径、币种和资产可兑换性一致时计算差额。卖方自填的模型 ID 不证明底层身份；未核实同款模型时也不计算差额。否则可并排展示挂牌价与独立的官方参考价资料，但明确标“不可比较”，不画划线价、不写“省 X%”。计价例子要按请求的真实输入/输出量算总费用。 |
| **演示资源** | `token2api-demo` 没有官方同款，官方参考价显示“不可比较”；本地 dUSD 可公开铸造、无兑付价值，不能写成美元折扣。 |

页面先按证据状态展示，避免用户把两列数字误读为已验证的节省额：

| 资源状态 | 模型广场展示 | 购买入口 |
| --- | --- | --- |
| 本地模拟资源 | 卡片显示“模拟资源”和卖方挂牌价（dUSD / 百万 Token）；共用说明写明无可比官方价与测试币属性，不展示划线价。 | 保留本地预算会话入口，在确认时提示测试代币和模拟用量。 |
| 真实网关、未核实型号 | 卖方声明的型号和挂牌价；官方参考资料可独立查阅，但显示“型号或计费条件未核实”，不算差额。 | 展示协议和最终用量验证状态；只对实际验收的能力开放购买。 |
| 已核实型号与计费条件 | 厂商来源、复核时间、标准价与卖方挂牌价；仅当币种和全部计费条件同口径时显示示例请求的总价及差额。 | 在确认页固定提供者、价格快照、预算、资金路径与退款规则，再请求授权。 |

价格来源可以从 [Anthropic 定价](https://platform.claude.com/docs/en/about-claude/pricing)、[OpenAI API 定价](https://developers.openai.com/api/docs/pricing)、[Gemini Developer API 定价](https://ai.google.dev/gemini-api/docs/pricing)等官方页面建立**人工复核的参考目录**，先不自动抓取无法长期保证稳定的网页。官方模型列表接口不一定包含实时价格。参考价过期或来源无法验证时隐藏折扣，留更新时间供用户判断。不同付款渠道的到账费用和退款方式另列，不把外部支付手续费混进 token 单价中。

| [gpt-6.1-sol / OpenAI API](https://developers.openai.com/api/docs/pricing) | $2.00 | $10.00 | 输入 ≤ 272,000 Token 的标准档；长上下文和缓存价格不同。 |

例如 1,000 输入 Token 与 500 输出 Token 的**公开价估算**，按上述 Claude Sonnet 5.5 标准价是 `1000 × 2 / 1,000,000 + 500 × 10 / 1,000,000 = $0.007`；这不包含缓存、工具、地区附加费用，也不是 Token2API 的报价。本地 demo 的 dUSD 无兑付价值，不能与该美元数值相减。只有确定卖方确实供应同一模型、同一服务条件和可兑换的付款资产后，才能计算可比总价。

## 买方与卖方：一键的实际含义

以下是目标用户旅程，其中工具导入、链下付款和卖方选择性导入尚未交付；每一步都需单独完成目标工具与账单验收。

**买方**：搜索并选择真实资源 → 查看费用示例及最坏预算占用 → 选择钱包托管或未来的链下付款 → 资金确认后创建仅绑定该会话的短期可撤销 Key → 点击 Magpie 或 CC Switch“添加提供者” → 在目标工具确认导入并选择模型 → 发起一次真实调用 → 在账单中看到请求、用量来源、费用和结算状态 → 关闭会话并处理余额。

**卖方**：在本机 CLI 或网页中主动选择一条已有网关配置（Magpie 或 CC Switch），预览将提交的域名、模型与权限，确认后只上传所选项的必要字段；凭证仅服务端密封保存，买方看不到。平台校验地址、模型实际响应、最终 usage 和上游请求 ID，运营者批准精确 origin，再由卖方输入挂牌价和并发限制、确认上架。导入订阅/服务账号前须确认其使用和转售权限。配置导入不等于获得上游资源的所有权或转售许可。

- [Magpie 官方导入规范](https://usemagpie.ai/docs/import)有 `https://usemagpie.ai/import#name=...&chat=...&key=...&models=...` 和 `magpie://import?...`；`chat` 指向 OpenAI Chat `/v1`。网页 fragment 不会发给 Magpie 站点，仍含买方密钥，必须在登录后即时生成、只在用户私密页面展示并请用户确认。
- [CC Switch 官方深链规范](https://github.com/farion1231/cc-switch/blob/main/docs/guides/deeplink-site-integration-guide-zh.md)是 `ccswitch://v1/import?resource=provider&app=...&name=...&endpoint=...&apiKey=...&apiFormat=...`。目标应用和协议必须一致；非原生格式需其本地路由。密钥在链接中，按凭证对待；导入弹窗由用户确认，默认不要替换其当前提供者。
- 这两种**买方导入链接**不是卖方资源自动上架 API。卖方配置在用户本机；网页不能静默读取。卖方导入先由 CLI 读取一条选中的本地记录，或在网页由用户主动粘贴并审阅；不上传整个备份、数据库或所有 Key。
- 当前 Token2API 强制每次请求提供新的、重试时保持不变的 `Idempotency-Key`，而这两个工具的提供者导入格式未承诺生成该动态请求头。现有接口还缺完整的 Claude Messages/Responses 协议、工具调用与更长上下文。**在真正端到端互通前，不显示“已支持一键使用 Claude Code/Codex”的按钮。**如开发受控本地适配器，它须生成并持久关联每个逻辑请求的键，处理重试、流式错误和审计，不能直接复用固定头。

## 支付方式：统一计量，分开资金责任

两种支付路径共享资源、报价快照、请求用量、预算预留和账单概念；**资金来源、退款及提供者提款**各自独立。每种路径都必须保证 `已扣费 + 未释放预留 ≤ 已确认资金预算`，明确异常请求保留预留并供人工核对。任何 Key 必须在资金确认后才能使用。

| 环节 | 钱包托管（已在本地演示） | 链下支付（规划） |
| --- | --- | --- |
| 充值/开通 | 用户签名授权并把可用测试 token 锁入合约；链上确认后开启会话。 | 支付机构确认成功后，平台记录可用预存余额，不能只凭前端“支付成功”提示放行。 |
| 调用计费 | 链下原子预留和用量核销；结算任务持久化，定期累计提交链上。 | 同一用量与预留规则；交易账、退款账、手续费账由独立资金账本核对。 |
| 卖方收入 | 合约按提供者地址累计可提现额，卖方发起 `withdraw`；收入与交易可核对。 | 平台经对账、风险准备及支付机构结算后转入卖方收款账户，展示到账时间和争议规则。 |
| 买方退款 | 会话关闭后未用预算进入原消费者地址的可提现额，再由其主动提现。 | 原路退回或退到账户余额，明确处理时间、手续费、拒付与坏账规则；不宣称链上即时退款。 |

EVM 链承担累计结算。每次请求在链下计量并预留预算，后台把确认的累计金额提交至会话所在链。实际到账时间受 RPC、确认深度、批次间隔、核对和提现影响。当前每套实例固定一个链与资产账本，不能直接替换旧合约。

## CLI 与 MCP：买卖双方都可以用

CLI 是批量操作和本机配置导入的入口；MCP 是 AI 助手调用市场工具的入口。命令和工具名以下是**拟定接口**，不是当前可执行命令。

| 身份 | CLI 拟定操作 | MCP 拟定工具 |
| --- | --- | --- |
| 买方 | `login`、`models search`、`quote`、`lease open`、`install magpie/cc-switch`、`usage`、`lease close`、`balance`、`withdraw` | `search_catalog`、`get_quote`、`prepare_lease`、`get_lease_status`、`list_usage`、`preview_refund` |
| 卖方 | `provider import --from magpie/cc-switch`、`provider probe`、`listing create`、`listing price`、`payouts` | `inspect_connector`、`draft_listing`、`preview_payout`、`list_settlements` |

`prepare_lease`/`draft_listing` 只准备待购买会话与上架草稿，不锁款、不激活 Key；扣款、开通会话、上架、关闭退款、提款等资金或供给写入操作须身份授权、用户可见的确认与状态查询，不能因模型生成一条工具调用就隐式执行。MCP 不持有上游密钥，不把浏览器 cookie 复用到第三方客户端。实际推理仍通过带限流与计量的版本化 REST；MCP 可返回购买链接、模型详情及账单摘要。上线远程 MCP 时独立设计 OAuth 权限、租户隔离、速率限制和 OpenAPI 对应的 REST 管理契约。[MCP 工具规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)建议敏感调用有可拒绝的人工确认，并要求服务端校验输入、访问控制和限流；[HTTP 授权规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)要求服务端核对令牌受众，不能直接把用户的推理 Key 当作远程 MCP 的管理权限。

**最小可验证版本**：先提供 `search_catalog`、`get_quote`、`prepare_lease`、`get_lease_status` 四个 MCP 工具。报价由服务端计算、有有效期和固定资源/价格/预算，准备会话只返回第一方支付页面链接；付款结果以收据和合约条款的服务端核验为准，不以模型生成的“已确认”或客户端回调为准。远程 MCP 按当前[授权规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)另建 OAuth 授权，不复用会话推理 Key；早期客户端需要协议互通测试。CLI 先做一份由项目维护的 Node 包，复用版本化 REST 管理接口；买卖双方密钥用隐藏输入或标准输入传递，持久保存到系统凭据库，不经命令行参数、日志或明文配置。[npm 包入口规范](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/)允许声明 `bin` 和运行时版本；发布前用 [`npm pack --dry-run`](https://docs.npmjs.com/cli/v11/commands/npm-pack/)检查打包内容。已交付商家本机连接器 CLI：`pnpm connector start/status`，通过出站 REST 领取持久化任务，本机 Key 不上传平台，支持文本流式回传、心跳、凭证重置和不确定用量保留预留。已通过隔离数据库与本地 HTTP/SSE 测试，真实上游与完整资金流仍需联调。已提供平台托管的独立 Node.js 安装包，商家安装 Node.js 24 后可在任意目录使用网页的 npx 命令，无需下载项目或配置数据库；构建时生成安装包，不依赖 npm 注册表发布。已保留独立 npm 发布入口，尚未发布到 npm，也不自动持久保存凭证。买方 CLI、通用管理命令、Magpie/CC Switch 配置自动导入与 MCP 仍未实现。详见[本机连接器](./LOCAL_CONNECTOR.md)。

## 建设顺序与验收证据

1. **可信模型广场**：在现有资源市场增加模型身份、协议能力与报价来源；先显示真实卖方挂牌价和“官方参考价未核实”的空态。补真实网关与官方价格来源后再开放有条件对比。后端以有来源/适用范围/校验时间的独立价格记录供给页面，前端只渲染服务端认定可比的价格，不能靠模型名字硬编码。验收：演示资源不出现虚假官方价，卖方不同报价分开呈现，价格变更不改旧会话快照。
2. **真可用的买方工具连接**：选一个客户端和一种协议，先抓取实际请求的格式与头，验证流/账单互通；解决动态幂等键、工具调用与真实用量，再接导入深链。验收：用户在目标工具完成实际任务、费用在预算内且能找到对应账单。先别把“成功导入配置”当作“成功使用模型”。
3. **卖方选择性导入与验收**：CLI 选一条网关配置、预览字段、验证所有权/协议/usage，运营者许可 origin，卖方确认价格后上架；加密钥轮换、下架和错误反馈。验收：一个外部卖方通过自己的网关交付一次可核对的真实请求，并完成收款。
4. **多链资金验收**：对每条链及每种资产，用两个真实钱包和获授权网关验证预算、调用、分账、退款和提现；记录交易费用与确认时间。
5. **链下付款再扩展**：选择支付机构，建立确认入账、预留、退款、拒付和卖方结算路径；与链上路径共用计量领域服务但不混用资金事实。验收：断网、重复回调、退款冲突及支付撤销均不能超支或重复分账。
6. **CLI 与 MCP**：CLI 复用上述 REST 管理能力和本机导入确认；MCP 优先只读发现、报价与账单，购买和上架用显式确认流程。验收：首次使用者无需理解数据库或手动编辑多份工具配置，也能完成从选择到调用和核对。

**并行实施分工与顺序**：两条模型广场任务已发给前后端会话。后端本轮完成会话 ID 消费者绑定、旧部署安全开通保护与本地资金队列验证；全仓验证和隔离新部署的端到端检查已通过。官方参考价数据、可信身份匹配、服务契约和测试列为后续独立范围。前端已完成独立小步：卡片标明卖方挂牌价与模拟资源，共用说明提供“暂无可比官方价”和测试币提示，预算弹窗说明价格快照，保留从资源到预算会话的路径；待后端契约明确后再增加官方参考价与有条件对比。此小步已在 320、375、768 和 1440 像素宽度做浏览器检查并通过定向 Biome 检查。双方共用上面的价格字段与“不虚构折扣”验收。CLI/MCP、买方深链与链下支付在 REST 管理契约、资金规则和目标工具互通测试明确后开始，避免只交付一个不能实际调用的导入按钮。
